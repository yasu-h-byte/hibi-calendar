# 出面入力

## 入力値
| 値 | 意味 | 色 |
|----|------|-----|
| 1 | 出勤（1日） | 緑 |
| 0.5 | 半日 | 黄 |
| P | 有給休暇 | 紫 |
| E | 試験（exam） | 青 |
| HK / ✈️ | 帰国期間（home_leave） | 水色 |
| R | 休み（rest） | グレー |
| H | 祝日扱い | グレー |
| 補（0.6） | 休業補償 | 紫 |
| 下段の数字 | 残業時間（0.5h単位） | オレンジ |
| 空欄 | 休み / 未入力 | — |

### AttendanceStatus 型と優先順位

`AttendanceStatus` 型: `'work' | 'overtime' | 'p' | 'compensation' | 'rest' | 'holiday' | 'home_leave' | 'exam' | 'empty'`

- `'home_leave'`（帰国期間）と `'exam'`（試験）を追加
- **UI 表示の優先順位（`getEntryStatus`）**: P > E > R > H > HK > 残業 > 出勤 > 未入力
  - スタッフ向け表示で「個別の休みの理由」を優先するため、HK より R/H が先
- **月次集計の優先順位（`lib/compute.ts`）**: HK が R/H より先に continue
  - 人工計算上、帰国期間中は労務集計の対象外として早期スキップする方が整合的

UI と集計でロジックが分離されているため、両者を改修するときは必ず両方の優先順位を確認すること。

## PC画面（管理者向け）
- 現場ごと・月ごとのグリッド入力
- 自動保存（入力するだけでOK）
- 配置編集ボタンでスタッフの現場割り当て変更
- 終了現場は「終了現場」チェックボックスで表示
- 年月セレクタ: 26ヶ月分（2024年4月まで遡れる）
- 日付ヘッダーと承認2行（職長承認・最終承認）はsticky固定（下にスクロールしても表示。承認行のtopオフセットはthead・職長承認行の実高さをuseLayoutEffectで実測して算出）
- 名前列・所属列はsticky固定（右にスクロールしても表示）

## スマホ画面（スタッフ向け）
- トークンURLでアクセス（ログイン不要）
- 欠勤届は日付選択式（デフォルト今日・min=今日で未来日も届出可。2026-07 追加。API `/api/attendance/staff` は元々任意日付対応で、承認ロック済み日・月次ロック済み月は従来どおり拒否）
- 「しゅっきん」ボタンで出勤登録（残業時間も設定可能）
- 「やすみ」ボタンで休み登録
- 「有給申請」ボタンで有給休暇を申請（残日数チェックあり）
- 過去5日分の入力履歴を確認・修正可能
- 日本語とベトナム語の二言語表示

### 出勤登録時の休憩チェックボックス
- 「午前休憩を取得した」「午後休憩を取得した」の2つのみ表示
- **昼休憩のチェックボックスは削除**（現場の昼休憩は基本的に必須のため、内部的に取得扱いで固定）
- チェック状態は実労働時間の計算に反映（後述の現場別勤務時間設定と連動）

### 道具代・有給残カード
- データがあれば即座に表示する（運用フェーズによるガードはなし）
- 道具代の控除期間表記は西暦付き `'2026/2/7 〜 2027/2/6'` 形式に統一

## フッター合計のルール
- 鳶合計 = とび + 職長 + 役員 + 外注（鳶）
- 土工合計 = 土工 + 外注（土工）
- 総合計 = 鳶合計 + 土工合計
- 外国人の補償（w=0.6）は人工数に含めない（compute()と統一）
- 浮動小数点は丸め処理（Math.round(n*10)/10）

## 出面の承認フロー（3段階）
1. **スタッフ**がスマホから出勤/休みを入力
2. **職長**がスマホ職長画面で確認・修正 →「この日を確認する」→ スタッフ入力ロック
3. **事業責任者（政仁さん）**がPC画面の「承認」行をクリックして最終承認

### 承認の影響
- 職長が確認 → スタッフの入力がロック（職長・管理者は編集可能）
- PC画面の承認行 → admin/approverロールがクリック可能（承認/承認解除）
- 承認データは `attendanceApprovals/{siteId}_{ym}_{day}` に保存

## 帰国フラグ(hk)と帰国申請の同期（必読）

**帰国フラグ `hk` は homeLongLeave から都度計算しているのではなく、出面ドキュメントへ
実際に書き込まれる実体データ**である。したがって帰国期間を変更したら、出面側も
書き換えなければ画面表示と実データがズレる。

### 2026-08-03 グエン タイン フウ事案

7/24〜12/1 で承認 → hk を書き込み → 開始日を 9/1 に変更、という操作で
**7/24〜8/31 の hk が消えずに残り**、出面入力画面が「7/30から帰国中」と表示した。
原因は、帰国期間を変更できる経路が5つあるのに、出面へ同期していたのが
「承認」の1箇所だけだったこと。期間を編集すれば誰にでも再現する構造的欠陥だった。

### ルール

- **帰国期間を触る処理は必ず `syncHomeLeaveAttendance()`（`lib/home-leave-sync.ts`）を通す。**
  対象は承認・手動登録・期間変更・削除・取消の全経路。出面へ直接 hk を書かない
- 同期は差分追跡ではなく **月単位の冪等な reconcile**。「その月のあるべき状態」に合わせるので、
  過去にどの経路で壊れたデータでも、その月を通せば必ず正しくなる
- **実績（出勤 w>0 / 有給 p / 休み r / 現場休 h / 試験 exam）が入っている日は触らない。**
  人が入力した実績を機械が消してはいけない
- **ロック済みの月は書き換えない**（給与確定後にデータが動くと支払額と食い違う）
- 「復帰未定」の終了日は番兵値 `9999-12-31`。素直に1日ずつ辿ると無限に書き込むため、
  書き込みは今月 +`HK_STAMP_HORIZON_MONTHS`（12ヶ月）で頭打ちにする。
  それより先の月は homeLongLeave の期間から直接判定して表示される

### 残骸の点検・掃除

休暇管理 →「✈️ 帰国情報」タブ →「🔍 出面の帰国表示を点検」から実行する。
検出（読み取り専用）→ 内容確認 → 削除、の二段構え。API は
`GET/POST /api/home-leave/reconcile`。

> `scripts/*.mjs` の診断スクリプト群は Admin SDK 移行（2026-06-29）以降、
> Firestore ルールの deny-by-default により **ローカルでは動かない**
> （Web SDK 経由のため `permission-denied`）。サービスアカウントは Vercel の
> 環境変数にしか無いため、この種の点検処理は API として実装すること。

## 現場別勤務時間設定

`Site` 型に `workSchedule` フィールドを追加し、現場ごとに始業・終業・休憩を上書き可能にした。

```typescript
workSchedule?: {
  startTime: string                                            // 例: '07:30'
  endTime: string                                              // 例: '16:30'
  morningBreak:   { enabled: boolean; minutes: number; mandatory: boolean }
  lunchBreak:     { enabled: boolean; minutes: number; mandatory: boolean }
  afternoonBreak: { enabled: boolean; minutes: number; mandatory: boolean }
}
```

### デフォルト（未設定の現場）
- 始業 8:00 / 終業 17:00
- 午前休憩 30分 / 昼休憩 60分 / 午後休憩 30分
- 1日の所定実労働時間 = 7h

### IHI現場（設定例）
- 始業 7:30 / 終業 16:30（9時間拘束、所定 7h）
- 休憩構成は会社デフォルトを踏襲
- スマホ出勤画面でこの現場を選択すると、表示される勤務時間が 7:30〜16:30 に切り替わる

### 連動する計算ロジック
- `types/index.ts` の `calcActualHours` / `calcOvertimeHours` は `workSchedule` を引数で受け取り、現場別の所定時間で実労働時間と残業時間を算出
- `lib/compute.ts` の月次集計も同じ workSchedule を参照して所定・残業を判定
- スマホ出勤登録の休憩チェックボックスは「enabled かつ mandatory ではない」休憩のみ表示


## 夜勤（台風待機など）— 2026-08 追加

年に数回、台風待機などで夜勤が発生する。**日勤で普通に働いて、そのまま夜間の現場待機に
入るケースがある**ため、1日1エントリの構造を保ったまま夜勤を別枠で持たせている。

### 入力方法（PC出面画面）— 2段階

**① 日付ヘッダーで「夜勤があった日」を指定する**

日付ヘッダーにマウスを乗せると日付の下に薄く「夜」が出る。クリックするとその日が
夜勤日になり、紫に塗られる。もう一度押すと解除。

**② その日のスタッフのセルで「夜」バッジを押す**

夜勤日に指定された日だけ、スタッフのセル左上に「夜」バッジが出る（未登録=白抜き、
登録済み=紫塗り）。押すと夜勤モーダルが開く。

この2段階にしているのは、全員・全日にバッジが出るとノイズになるため。
夜勤は年に数回なので、まず日を絞ってから人を選ぶ。

夜勤日の指定は `main.nightDays[siteId_ym]` に日のリストとして保存される。
**誰が夜勤したかはエントリ側の `ns` が持つ**ので、この指定は入力対象日を絞る
UIフィルタでしかない（給与計算・所定日数には一切影響しない）。
日の指定を解除しても、既に登録済みの夜勤エントリは消えない（誤操作で給与が変わらないため）。
個別の取り消しはモーダルの「夜勤を取り消す」から行う。

モーダルで入力する項目:

| 項目 | 内容 |
|---|---|
| この日の勤務 | 「日勤＋夜勤」か「夜勤のみ」を選ぶ |
| 夜勤の始業 | 15:00〜23:30（日勤の続きで入る待機に対応するため夕方から） |
| 夜勤の終業 | 20:00〜翌9:00。24時以降は「翌5:00」のように表示される |
| 夜勤中の休憩 | 分単位（既定60分） |
| 理由 | 「台風待機」など。後から労働時間性を説明できるように残す |

モーダルには夜勤の実労働時間・深夜時間・その日の人工が即時表示される。

### データ構造

```typescript
ns?: number     // 1 = この日に夜勤あり
nonly?: number  // 1 = 夜勤のみ（日勤なし）。日勤＋夜勤なら未設定
nst?: string    // 夜勤の始業 "20:00"
net?: string    // 夜勤の終業 "29:00" ← 24時超え表記（=翌5:00）
nb?: number     // 夜勤中の休憩（分）
nnote?: string  // 理由
```

**終業を "29:00" のような24時超え表記で保存する**のが設計の要点。`timeToMinutes("29:00")`
が 1740 を返して単調増加になるため、`calcDayShiftHours` / `calcNightMinutes` が
日付またぎの特別扱いなしで正しく動く。画面表示は `formatTimeLabel()` が「翌5:00」に変換する。

### ⚠️ w（出勤日数）は夜勤があっても 1 のまま

夜勤を `w: 1.5` のように表現してはいけない。`workDays` が 1.5 日になり、
**欠勤判定（所定日数 − 出勤日数）が壊れる**。人工は `calcManDays()` が `ns` から導出する。

| ケース | w | ns | nonly | 出勤日数 | 人工 |
|---|---|---|---|---|---|
| 日勤のみ | 1 | — | — | 1 | 1 |
| 半日のみ | 0.5 | — | — | 0.5 | 0.5 |
| 夜勤のみ | 1 | 1 | 1 | 1 | 1.5 |
| 日勤＋夜勤 | 1 | 1 | — | 1 | 2.5 |
| **半日＋夜勤** | 0.5 | 1 | — | 0.5 | **2.0** |

### 実際の運用は「日勤 → 残業 → 22時から夜勤」の3段構成

2026-08-11 笹塚の台風待機の実例:

| 時間帯 | 扱い | フィールド |
|---|---|---|
| 13:00〜17:00 | 半日出勤 | `w = 0.5` |
| 17:00〜22:00 | 残業5時間 | `o = 5` |
| 22:00〜翌5:00 | 夜勤 | `ns/nst/net` |

**残業（`o`）と夜勤（`nst`〜`net`）は時間帯が重ならないので二重計上ではない。**
「22時までは残業、22時からが夜勤」という区切りで運用しているため、夜勤エントリに
`o` が同居しているのは正常。したがって「夜勤があるのに残業欄も入っている」ことを
警告してはいけない（毎回誤検知になる）。夜勤の始業の初期値を 22:00 にしているのもこの運用に合わせたもの。

この日の支給は 人工2.0（半日0.5＋夜勤1.5）＋ 残業5h。実労働15h・深夜6h に対する
法定必要額は日額の2.28倍で、実支給2.78倍がこれを上回るため警告は出ない。

**夜勤は日勤の長さに関係なく常に 1.5人工**（独立したシフトとして数える）。
日勤ぶんは `w` がそのまま人工になるので、午後から出勤（0.5）してそのまま待機に入った
日は 0.5＋1.5＝**2.0人工** になる。2.5 にはならない。

### ⚠️ 人工の集計は必ず calcManDays を通す

`entry.w` を直接足すと夜勤の 1.5人工 が抜ける。2026-08-13 に
`computeWorkerTotals`（人ごとの合計欄）と `computeFooterSums`（鳶計・土工計・総計）で
実際にこのバグが出た。セルの「2人工」表示・給与計算・元請け請求とだけ食い違うので
気づきにくい。

- 人工が欲しい場所 → `calcManDays(entry)`
- 出勤**日数**が欲しい場所 → `entry.w`（夜勤で日数は増えない）

出勤率の計算（`lib/attendance-rate.ts`）は `Math.min(workSum, 1)` で日数に丸めているため
`entry.w` のままで正しい。

**Excel帳票（`generateHibiAttendance` / `generateHfuAttendance` /
`generatePerSiteAttendance`）は未対応**。`entry.w` を使っているので夜勤ぶんが出ない。
社労士提出用は「出勤日数」であるべきで請求用は「人工」であるべき、と用途が分かれるため
方針決定待ち。

### ⚠️ 残業h（o）に夜勤を混ぜない

`calcActualHours()` は日勤＋夜勤の**合計**を返す。一方、残業時間の自動算出には
`calcDayShiftHours()`（日勤のみ）を使う。夜勤は人工で別途支給するため、
残業hに混ぜると二重計上になる。

- 実労働の合計が欲しい場所 → `calcActualHours()`
- 残業hを出す場所 → `calcDayShiftHours()`
- 夜勤ぶんだけ欲しい場所 → `calcNightShiftHours()`

### 22時以降は必ず夜勤として登録する（運用ルール）

日本人は日給月給でレガシー入力（出勤値＋残業h）のため始業終業の時刻を持たず、
深夜時間を時刻から判定できない。**22時以降に働く場合は必ず夜勤として登録する**
という運用で深夜労働の対価を担保している（2026-08-12 代表確認）。

残業欄だけに長時間を入れると深夜割増も1.5人工も付かないため、
`lib/compute.ts` が「現場の終業時刻 ＋ 残業h > 22:00 かつ夜勤登録なし」の日を
検出し、月次画面に「⚠ 夜勤未登録○日」の琥珀バッジを出す。
