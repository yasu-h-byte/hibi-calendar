## 1. このシステムは何のためのシステムか

**「誰が・いつ・どの現場で・どれだけ働いたか」という1つの事実（出面）を正しく確定し、そこから出るお金と法令の書類を、
食い違いなく出すためのシステム。**

出面という1つの事実から、3つの流れが出る。

| 流れ | 何を出すか | 相手 |
|---|---|---|
| 払う | 給与の元データ（月次集計・計算根拠・出面一覧 ほか5点）、外注費 | キャシュモ（両社）、同業者 |
| もらう | 請求書と出面明細、HFU → 日比建設 の請求書 | 元請・同業者 |
| 守る | 就業カレンダーと同意の記録、有給管理簿、年5日の取得、在留期限、記録の保存 | 労基署・監理団体・本人 |

そこに2つの流れが乗る。

| 流れ | 何を出すか | 相手 |
|---|---|---|
| 経営の判断 | 現場別の人工・売上・原価・粗利 | 代表、経営コックピット |
| 人を育てる | 評価・昇給・号俸・賞与・道具代・書類 | 本人、政仁さん、代表 |

この会社ならではの難しさは3つある。

1. **2つの会社**（日比建設・HFU）で、締め・帳票・請求が別々に進む
2. **3つの賃金の形**（日本人の日給月給と号俸、ベトナム人の時給ベース月給と変形労働時間制、旧契約の固定月給）が同じ出面から計算される
3. **現場が動く**（工種で単価が違う・応援で他社の現場に入る・スポット現場・月の途中で配置が変わる）

使う人は5種類で、求めるものが違う。

| 人 | 道具 | 知りたいこと・やること |
|---|---|---|
| スタッフ（ベトナム人・日本人） | スマホ | 今日の打刻、休みの申請、自分の出面と給料が合っているか |
| 職長 | スマホ | 昨日までの出面の承認、翌月のカレンダーの提出 |
| 政仁さん（事業責任者） | PC・スマホ | 最終承認、月締め、請求の承認、評価 |
| 森田さん（事務） | PC | 締めの準備、キャシュモへの提出、有給・道具代・請求の事務 |
| 代表 | PC | 仕組みの管理、原価と粗利、賃金の設計 |

### だから、システムが守るべき約束は4つ

1. **事実は1つ**：同じ出面から出た数字は、どの画面・どの帳票でも同じになる
2. **順番を守る**：本人の入力 → 職長の承認 → 最終承認 → 本人の確認 → 締め → 提出・請求。前の段がそろわないと次に進まない
3. **締めたら動かない**：締めた月の数字は、あとからマスタを変えても変わらない。変わったら必ず気づける
4. **見てよい人だけが見る**：個人の給与は3人だけ。現場のことは現場の職長だけ

今週見つかった不具合のほとんどは、この4つのどれかが破れたものだった。

## 3. 今週の不具合を根本から見ると（7つの型）

9/28〜10/2 の約100件の修正と、今回の点検で見つかった約95件を並べると、原因は7つの型に集まる。
型ごとに「同じ穴が二度と開かない仕組み」を入れる。

| 型 | 何が起きていたか | 今回入れる仕組み |
|---|---|---|
| ① 同じ判定を画面ごとに数え直す | 在籍・配置・未入力・締め済み・承認済みを、画面や API がそれぞれ自前で計算して食い違う | 判定を共通の関数に寄せ、自前で書いたらテストが落ちるようにする |
| ② 「並べる方式」の足し忘れ | 担当現場チェックの対象・給与で消す項目・バックアップの対象を1つずつ並べていて、あとから足したものが抜ける | 「既定で安全側・外すものだけ並べる」に反転し、網羅のテストを足す |
| ③ 画面だけで守っている | 画面はボタンを止めているが、サーバは止めていない（先の日の承認・最終承認済みの日の修正・カレンダーの法定チェック） | 同じ判定をサーバにも入れる |
| ④ 保存の結果を見ない | サーバが断っても画面は「保存済み」「承認済み」のまま | 保存の共通部品で結果を必ず見て、失敗は戻して理由を出す |
| ⑤ 「いつの時点か」の取り違え | 退職「予定」の人が退職済み扱い／締めた月を今のマスタで計算し直す／有給の期／日本時間 | 日付で判定する共通の関数（退職は日付で見る）。lint をエラーにする |
| ⑥ 2社・親子の現場のキー | 片方の会社だけ締めた月に書ける／工種サイトの打刻が親の集計に出ない | 人の会社で締めを見る共通の関数。現場は親にそろえる関数を通す |
| ⑦ 資料が画面と別々に古くなる | 今週変えたルール（有給は前日まで・付与日・紙の請求書）がマニュアルに残っていない | マニュアルを改訂。画面名との突き合わせを提案 |

## 4. 今回直したもの（約90件・13コミット）

6つの領域を点検し、同じエージェントが担当ファイルを分けて修正した。すべて本番と同じビルド・全テスト（113ファイル・1,222件）・各 lint を通している。
利用者向けのお知らせは `lib/release-notes.ts` に6件。

### 4-1. 承認と締めの流れ（約束②「順番を守る」）
- PC の「まとめて承認」が月末まで先の日も承認していた → 昨日までの入力がある日だけ。サーバも先の日・実在しない日を断る
- 承認・取り消しがサーバで断られても画面は承認済みのままだった → 結果を見て戻し、理由を出す
- 片方の会社だけ締めた月に、スマホ・職長画面・工種の移動・履歴の復元・運転者から書けた → 「その人の会社で締めを見る」共通の関数に一本化
- 最終承認済みの日を職長・事務がサーバ経由で変えられた → 政仁さん・代表だけ（画面と同じ判定をサーバにも）
- 出面を書く経路が6つあり検査がばらばら → 共通の保存入口（`lib/attendance-save.ts`）。履歴・残骸の掃除・移動の1回書きもここに
- 半日（0.5）が「未入力」に数えられていた／別現場で入力している人が「未入力」に出ていた／配置の決め方が2通り／職長トークン画面の現場が「今月の職長」固定
- 0.6補（会社都合休）を休みの日に入れられた／前月コピー（出面を丸ごと上書き）を廃止／所定日数の保存に権限・締め・記録が無かった

### 4-2. 給与計算と帳票（約束①「事実は1つ」・③「締めたら動かない」）
- 旧契約の固定月給で欠勤が多い月に支給がマイナスになった → 基本給を下限に
- 同じ日に2現場へ「欠」を入れると二重控除 → 日単位で1回
- 計算根拠PDFに【未確定（締め前）】の印が無かった → Excel と同じ条件で印。休業手当の行・最低20日保証の内訳・帰国日数・出向者も載る
- 月が終わってから終了にした現場の出面が、出面一覧・勤怠サマリーから落ちていた → 「その月に出面がある現場」は載せる
- 月次集計Excelのベトナム人シートに欠勤を検算する列が無かった → 枠内補償日・試験日・帰国日数・保証枠・本人の欠勤を追加（両社同じ）
- 給与チェックに「注意点」を追加（支給は変えない・9月分から）。判断待ちの7項目（§5）をここで知らせる
- 出向の判定が原価側と請求側で別のデータを見ていた → 1つに
- テストを3種追加: 「働いた分を下回らない」不変条件（新ルール2,000通り）、帳票どうしの突き合わせ、9月分・10月分の合成ゴールデン

### 4-3. 有給・就業カレンダー（約束①・⑤）
- 月末（29〜31日）入社の人の初回付与が拒否され、以後も毎年1段階少なかった（法定割れ） → 勤続月数の数え方を直し、入社日731日×8段階の総当たりで固定
- 「付与待ち」からのまとめて付与が、10/1 の日本人の正しい日数を「法定超」と見て全員分を拒否していた
- 精勤賞与の買取が「期末＝9/30」固定で、/leave の表示と食い違った → 「支給日の時点で終わっている期」の残で統一
- 期が終わって次の付与がまだの間、申請の残数チェックが効かなかった → 残0・「付与の手続き待ち」で止める。通知も付与するまで消えない
- 有給の最終承認がその日の出勤入力・承認を黙って上書きした → 確認つき。日付変更の失敗で元の日の有給だけ消えた → 順序を直す
- 有給管理簿Excel（法定帳簿）の取得日数に買取が混ざる・来年分を読まない・日本人の繰越・重なる期間 → 画面と同じ関数に
- 承認済みカレンダーをサーバ経由で職長が法定チェックなしに直せた／一括確定が承認済みの現場を上書きして再署名が出た／法定チェックが月をまたぐ週を見なかった

### 4-4. 権限と秘匿（約束④「見てよい人だけ」）
- 人員マスタの update が「送られたキーを何でもマージ」で、適用開始日・直前の日額を事務が書き換えられ監査にも残らなかった → 許可リスト。給与欄は代表だけ・新規登録も同じ
- 退職しても通行証・個人パスワード・スマホURLが使えた → 退職日の翌日から無効（URLは翌月末まで見るだけ）。逆に、退職「予定」日を入れた瞬間に退職扱いになりログインできなかった → 日付で判定（lint を「落とす」に）
- 事務が政仁さん・代表のスマホURL（最終承認の鍵を兼ねる）を読める・発行し直せた → 代表だけ。合言葉を長く
- 職長が API を直接呼ぶと他現場の配置・運転者・夜勤日を書けた → 担当現場チェックを「既定で対象」に反転
- 通行証の署名鍵がパスワードそのもの → 環境変数 SESSION_SECRET を足せる（§7）。ログインの比較を定数時間に
- cron（時効処理）が合言葉未設定なら誰でも動かせた・合言葉が URL に載った → 3本とも共通の鍵（ヘッダだけ・未設定は拒否）
- 画面のJSに HFU の口座番号・登録番号が直書き／移行データ（実名・金額）が server-only でなかった／公開資料の検査がすり抜けた
- 評価 API の「消す項目を並べる」方式を許可リストに。500 でスタックトレース。?password= の廃止。セキュリティヘッダ

### 4-5. 請求・原価・運用基盤
- 請求書の採番と「同じ会社・同じ月は1件」が同時操作で破れた → トランザクション
- 紙の請求書の側からの二重請求を止めていなかった／同じ月に紙が2枚あると必ず「差あり」 → 両方向で止め、合算で見比べ、小計＋税＝合計の確認
- /cost の月次で終了現場の売上だけ消えて粗利が少なく出た → 「その期間に人工・原価・請求額がある現場」を /cost・ダッシュボード・連携で共用
- 現場・取引先を使用中でも削除できた／取引先を保存すると現場別の残業単価が消えた／代理職長の選択肢が常に空（職種を日本語で比較）
- main の読み書きが丸ごと置換で同時編集が消えた／請求額の変更に記録が無かった／操作ログを1件書くたびに550件読んでいた
- 日次バックアップに承認の記録・本人確認・書類庫・給与欄の変更記録が入っていなかった／古い分が永久に消えなかった／失敗しても気づけなかった → 対象の一覧を1か所に（足し忘れはテストが落とす）・結果を記録して通知ベルと稼働確認に

### 4-6. 画面と資料（約束④・⑦）
- 保存失敗が「保存済み」に見える箇所（配置・所定日数・請求額・道具代・代理職長・転籍・URL発行・削除 ほか）→ 結果を必ず見る
- 人員マスタで「消す・外す」変更が保存されず、誤った退職日を画面から消せなかった／号俸欄が外国人側の分岐の中で出なかった／年次改定で続けて評語を変えると前の人が戻った
- 未保存のまま右パネルを閉じると消えた → 確認（共通部品）。出面のセル入力は離脱時も送る
- ダッシュボードの却下が1クリックで理由なし → 理由を入れて確定。権限の無い人に編集ボタン
- スタッフ画面: 前日から開きっぱなしだと前日の日付で保存／「今日は登録済み」が残らない／取得が二重に走る／ベトナム語の欠け／押しづらい大きさ
- 月を速く切り替えると前の応答が後から届いて混ざる → 古い応答を捨てる共通フック
- マニュアル8冊と仕様書6本を今週のルールに合わせて改訂（§6）。リポジトリに誤って登録されていた node_modules のリンク・作業用フォルダを除去
