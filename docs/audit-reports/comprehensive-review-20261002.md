## 1. このシステムは何のためのシステムか

**「誰が・いつ・どの現場で・どれだけ働いたか」という1つの事実（出面）を正しく確定し、そこから出るお金と法令の書類を、
食い違いなく出すためのシステム。**

出面という1つの事実から、3つの流れが出る。

| 流れ | 何を出すか | 相手 |
|---|---|---|
| 払う | 給与の元データ（月次集計・計算根拠・出面一覧 ほか5点）、外注費 | キャシュモ（両社）、同業者 |
| もらう | 請求書と出面明細、HFU → 日比建設 の請求書 | 元請・同業者 |
| 守る | 就業カレンダーと同意の記録、有給管理簿、年5日の取得、在留期限、記録の保存 | 労基署・監理団体・本人 |

そこに2つの流れが乗る。

| 流れ | 何を出すか | 相手 |
|---|---|---|
| 経営の判断 | 現場別の人工・売上・原価・粗利 | 代表、経営コックピット |
| 人を育てる | 評価・昇給・号俸・賞与・道具代・書類 | 本人、政仁さん、代表 |

この会社ならではの難しさは3つある。

1. **2つの会社**（日比建設・HFU）で、締め・帳票・請求が別々に進む
2. **3つの賃金の形**（日本人の日給月給と号俸、ベトナム人の時給ベース月給と変形労働時間制、旧契約の固定月給）が同じ出面から計算される
3. **現場が動く**（工種で単価が違う・応援で他社の現場に入る・スポット現場・月の途中で配置が変わる）

使う人は5種類で、求めるものが違う。

| 人 | 道具 | 知りたいこと・やること |
|---|---|---|
| スタッフ（ベトナム人・日本人） | スマホ | 今日の打刻、休みの申請、自分の出面と給料が合っているか |
| 職長 | スマホ | 昨日までの出面の承認、翌月のカレンダーの提出 |
| 政仁さん（事業責任者） | PC・スマホ | 最終承認、月締め、請求の承認、評価 |
| 森田さん（事務） | PC | 締めの準備、キャシュモへの提出、有給・道具代・請求の事務 |
| 代表 | PC | 仕組みの管理、原価と粗利、賃金の設計 |

### だから、システムが守るべき約束は4つ

1. **事実は1つ**：同じ出面から出た数字は、どの画面・どの帳票でも同じになる
2. **順番を守る**：本人の入力 → 職長の承認 → 最終承認 → 本人の確認 → 締め → 提出・請求。前の段がそろわないと次に進まない
3. **締めたら動かない**：締めた月の数字は、あとからマスタを変えても変わらない。変わったら必ず気づける
4. **見てよい人だけが見る**：個人の給与は3人だけ。現場のことは現場の職長だけ

今週見つかった不具合のほとんどは、この4つのどれかが破れたものだった。

## 3. 今週の不具合を根本から見ると（7つの型）

9/28〜10/2 の約100件の修正と、今回の点検で見つかった約95件を並べると、原因は7つの型に集まる。
型ごとに「同じ穴が二度と開かない仕組み」を入れる。

| 型 | 何が起きていたか | 今回入れる仕組み |
|---|---|---|
| ① 同じ判定を画面ごとに数え直す | 在籍・配置・未入力・締め済み・承認済みを、画面や API がそれぞれ自前で計算して食い違う | 判定を共通の関数に寄せ、自前で書いたらテストが落ちるようにする |
| ② 「並べる方式」の足し忘れ | 担当現場チェックの対象・給与で消す項目・バックアップの対象を1つずつ並べていて、あとから足したものが抜ける | 「既定で安全側・外すものだけ並べる」に反転し、網羅のテストを足す |
| ③ 画面だけで守っている | 画面はボタンを止めているが、サーバは止めていない（先の日の承認・最終承認済みの日の修正・カレンダーの法定チェック） | 同じ判定をサーバにも入れる |
| ④ 保存の結果を見ない | サーバが断っても画面は「保存済み」「承認済み」のまま | 保存の共通部品で結果を必ず見て、失敗は戻して理由を出す |
| ⑤ 「いつの時点か」の取り違え | 退職「予定」の人が退職済み扱い／締めた月を今のマスタで計算し直す／有給の期／日本時間 | 日付で判定する共通の関数（退職は日付で見る）。lint をエラーにする |
| ⑥ 2社・親子の現場のキー | 片方の会社だけ締めた月に書ける／工種サイトの打刻が親の集計に出ない | 人の会社で締めを見る共通の関数。現場は親にそろえる関数を通す |
| ⑦ 資料が画面と別々に古くなる | 今週変えたルール（有給は前日まで・付与日・紙の請求書）がマニュアルに残っていない | マニュアルを改訂。画面名との突き合わせを提案 |
