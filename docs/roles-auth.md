# ロール・認証・権限

## 認証方式（2026-09-26 改訂）
- 個人パスワード: 事業責任者・役員・事務（政仁さん・森田さん等）は個人パスワードで直接ログイン（名前選択不要）。設定 → 個人パスワード設定（代表のみ）
- 職長: 共通パスワード（環境変数 ADMIN_PASSWORD）→ 名前を選択（在籍中の職長だけ選べる）。
  **ログイン時にサーバーが本人の通行証（`lib/session-token.ts`・90日）を発行し、以降の API はその通行証で本人を特定する**。
  共通パスワードそのものは API では通らない（旧: 共通パスワード＝誰か分からない管理者扱いで、職長が管理者専用の API を叩けた）
- スーパー管理者（代表）: 環境変数 SUPER_ADMIN_PASSWORD（直接ログイン）
- スタッフ: トークンURL（ログイン不要・別の仕組み）
- 通行証導入前にログインしたままの職長、パスワード変更・通行証の期限切れは、管理画面を開いたときにログイン画面へ戻る（heartbeat 401）
- **API に届くのは通行証だけ**（2026-09-26）: 代表 `st1`（30日）・事務/役員/事業責任者 `pt1`（30日・パスワードの指紋入り＝変更・削除で無効）・
  職長 `ft1`（90日）。パスワードそのものはログイン（/api/auth）だけが受け付け、ブラウザには保存しない
- 個人パスワードは **scrypt でハッシュ化して保存**（lib/password.ts）。設定画面は「設定済み／未設定」だけを表示し、
  新しいパスワードの入力（8文字以上・他の人や共通パスワードと重複不可）と削除のみ。保存時に古い平文も全員分ハッシュ化される
- **読み取りも権限表どおり**: 給与・売上・有給・請求の API は事務所の人だけ。職長の画面で使う人員・現場・評価の API は
  中身を役割で絞る（給与欄・電話URL・単価・他人の評価と昇給額を返さない）
- **自動点検**: `__tests__/api-auth-coverage.test.ts` が、すべての API 処理が requireCap 等か `// auth: <理由>` で
  「誰が呼べるか」を明示しているかを確かめる（付け忘れはテストが落ちる）
- **通行証の退職判定**（2026-10-02 総合点検・`lib/auth.ts` `isTokenHolderActive`）: 通行証は署名と期限に加えて、人員マスタ（30秒キャッシュ）の退職日を見る。
  **退職日の当日までは使え、翌日からは通らない**。人員マスタに居ない人も通さない（旧: 退職した職長の通行証は最長90日、事務・役員の個人パスワードは代表が消すまで使えた）。
  人員マスタが読めないとき（クォータ超過など）は今までどおり通す（読み取り障害を全員締め出しにしない）
- **通行証の鍵 `SESSION_SECRET`**（`lib/session-token.ts`）: 環境変数 `SESSION_SECRET`（32文字以上のランダム文字列）があれば署名鍵に**足す**（鍵＝SESSION_SECRET＋代表パスワード＋共通パスワード）。
  短すぎる値は設定ミスとみなして使わない。**設定した瞬間に全員の通行証が無効になる**（全員ログインし直し。設定は代表が Vercel で行う）
- **スタッフ・職長の合言葉（スマホURL）の有効期間**（`lib/workers.ts` `staffTokenStateOf`・2026-10-02）:
  `active`＝在籍中（退職日の当日まで・全部使える）／`grace`＝退職日の翌日〜**退職した月の翌月末**（見るだけと、最後の月の本人確認だけ。`allowGrace: true` を付けた入口＝
  本人の出面画面の GET・本人確認だけが通す。書く側の POST・マイページは在籍中だけ）／`expired`＝それ以降は無効。退職日が日付でない古いデータは `expired`
- **管理者側の合言葉は代表だけ**（2026-10-02）: 代表（0）・政仁さん（1）・役員・事務のスマホURL（合言葉）は最終承認などの鍵を兼ねるので、`/api/workers` は `system.admin` の人にだけ返す
  （画面には `tokenHidden: true` で「代表のみ」）。旧: 事務が政仁さんの合言葉を読んで最終承認まで一人でできた

## ロール一覧
| ロール | 日本語表示 | 判定方法（`lib/auth.ts` buildAuthUser） | 対象者 |
|--------|-----------|----------|--------|
| admin | 代表 | スーパー管理者パスワード（workerId 0）だけ | 靖仁さん |
| approver | 事業責任者 | workerId === 1 | 政仁さん |
| officer | 役員 | 職種「役員」（政仁さん以外） | — |
| jimu | 事務 | 職種「事務」 | 森田さん |
| foreman | 職長 | 職種「職長」／現場の職長設定 | 白戸・大川・日比大介 |

役割が決まらない人は最小権限（担当現場なしの職長）に落ちる（旧: 何でもできる admin に落ちていた）。

## 役割ごとの権限（**`lib/permissions.ts` が唯一の決まり**）
メニューの表示（`lib/menu.ts`）・画面のボタン・サーバーのチェック（`lib/auth.ts` の `requireCap`）・
設定画面の権限表（ユーザータブ・見るだけ）は、すべて `lib/permissions.ts` の `CAPABILITIES` を読む。
旧実装はメニューの役割直書き・MENU_ID_MAP・設定画面のチェックボックス（Firestore `rolePermissions`）の
3か所が食い違っていたため廃止した（2026-09-26 代表決定）。

原則: 現場の作業は職長、事務処理は事務、最終承認は事業責任者、システムは代表。役員（政仁さん以外）は事業責任者と同じものを見るだけ。

代表決定（2026-09-26）:
- 有給の付与・時季指定・買取の記録は事務（森田さん）もできる。有給・帰国申請の最終承認は政仁さん（と代表）だけ
- 人員マスタの給与欄（時給・号俸・日額・月給・残業倍率・旧ルール）の**直接の書き換えは代表だけ**。
  事業責任者は評価の承認・号俸の改定を通して決める。事務は基本情報・電話URLを編集できる
- 原価・収益は事業責任者も使える（請求額の入力も可）
- 出面: 入力は職長（担当現場）・事務（漏れのフォローと過去日の修正）、職長承認は職長、最終承認は事業責任者。変更履歴・復元は事務も可
- 請求書: 事務が申請 → 事業責任者が承認して発行（docs/peer-invoice.md）。申請・取り下げ `invoice.request` は **事務＋政仁さん＋代表**（2026-10-02・権限表で判定。旧は画面ごとの直書き）、
  承認・発行・取り消し `invoice.approve` は政仁さん＋代表、紙で出した請求書の登録・修正 `invoice.paper` は事務＋政仁さん＋代表
- システム設定・パスワード・バックアップ・アクセス履歴・お知らせ投稿・出面データの保守ツールは代表だけ

担当現場の制限（職長は自分の現場だけ）は権限表とは別に各 API がチェックする（`lib/attendance-authz.ts` 等）。
権限を変えるときは `lib/permissions.ts` の1行を直す（メニュー・画面・サーバー・設定画面の表に同時に反映される）。

## 給与を見られる人（2026-10-02 代表）

個人の給与（時給・日額・月給・支給額・昇給額・号俸）は **靖仁さん（0）・政仁さん（1）・森田さん（303）だけ**。
役割（事務・事業責任者・代表）と本人（`PAY_VIEWER_WORKER_IDS`）の**両方**がそろったときだけ、給与の権限（`PAY_CAPS`）が通る。

| 給与の権限（PAY_CAPS） | 内容 |
|---|---|
| `pay.view` | 人員マスタの給与欄・ダッシュボードの金額つきの注意（法定割増の不足・時給の改定） |
| `monthly.view` / `monthly.close` | 月次集計・締め・帳票（支給額を含む） |
| `cost.view` / `cost.edit` | 原価・収益（人件費を含む） |
| `wage.view` / `wage.decide` / `wageAnalysis.view` | 賃金・評価・昇給・賃金分析 |
| `workers.editPay` / `cockpit.view` | 給与欄の書き換え・経営コックピット |
| `workers.edit` | 人員マスタの編集・スタッフのスマホURL（本人ページに欠勤控除の日額などが出るため・2026-10-02 総点検） |
| `staffDocs.view` / `staffDocs.edit` / `staffDocs.delete` | 書類庫（雇用契約書に賃金が書いてあるため） |

ほかに、休暇管理の有給買取の金額（精勤賞与の額）は `pay.view` の人にだけ返す。
`/api/workers` は相手ごとに返す項目を許可リストで決める（`lib/workers.ts` の WORKER_PAY_KEYS / WORKER_OFFICE_KEYS / WORKER_PUBLIC_KEYS）。

**給与欄の書き込みも許可リスト**（2026-10-02 総合点検・`app/api/workers/route.ts`）: add / update の body は「書いてよい項目」だけに絞り、
給与欄 `WORKER_OWNER_ONLY_KEYS`（＝`WORKER_PAY_KEYS` ＋ `useOldRules`。日額・時給・月給・号俸・残業倍率・適用開始日・前の額・予定表・旧ルール）は
**新規登録でも代表（`workers.editPay`）だけ**が入れられる（事務が入れると 403「給与欄を入れられるのは代表だけです」）。
更新は「値が変わるとき」だけ判定し、**空で送る（消す）も変更**として扱う。旧は手書きの一覧が2つあり、rateFrom・prevRate などの消し漏れがあった。
給与欄の変更は `auditTrail` に残す。

- 役員（officer）・職長・奥寺さん（301）・佐藤さん（302）は、役割に関係なく給与を見られない
- 画面は `lib/page-guard.ts` が入口で止め、API は `requireCap` / `callerCan` が止める。資料は `npm run lint:pay`
- 見られる人を変えるのは代表の指示があるときだけ

## ロール変更方法
- 人員マスタの「職種」を変更すると連動（役員→officer、職長→foreman、事務→jimu）
- 政仁さん（ID:1）はハードコードで approver 固定
- **日比靖仁さん（ID:0・代表・開発者）は、代表パスワードでも個人パスワードでも代表（owner・全権限）**（2026-10-01 代表指示）。
  `lib/auth.ts` の `OWNER_WORKER_ID`。個人パスワードの通行証も API では 'super-admin' として扱う。
  旧: 職種が役員なので個人パスワードでは「役員（見るだけ）」になり、電話URLの発行状況などが見えなかった

## 職長承認ができる人・政仁さんの代行（2026-10-01 代表決定）

職長承認（出面・有給申請・帰国申請）ができるのは、次の**両方**にあてはまる人だけ。

1. その月にその現場の職長として登録されている（現場マスタの職長、または月別の職長 mforeman）
2. 人員マスタの職種が「職長」（jobType / job = `shokucho`）

職長でない人（とび・役員など）が現場マスタの職長に登録されている現場は、**政仁さん（事業責任者）が職長承認を代行**する。
- 判定は `lib/auth.ts` の `approvingForemenOfSite` / `isProxyApprovalSite` の1か所（出面・有給・帰国申請・通知・マイページで共通）
- 出面の代行は `attendance.foremanApproveProxy`（事業責任者・代表）。有給・帰国申請は管理者・事業責任者がもともと現場を問わず職長承認できる
- 出面の**入力**の権限は変えない（承認だけの決まり）。応援現場で政仁さんが入力〜承認する決まり（`attendance.inputSupport`）もそのまま
- **さかのぼり入力**（`attendance.backfill`・2026-10-02 代表決定）: 代表と政仁さんだけ。本人（外国人スタッフ）の入力が無い昨日までの日に、
  出勤・有給・欠勤・0.6補を新しく入れられる。PC の出面入力で「今から変更する」を押したときだけ選択が出る。
  政仁さんは attendance.input を持たないが、**昨日までの日なら入力のある日の上書き・削除・外注の人工も直せる**（同日 代表判断で広げた。
  経緯: 一度「入力の無い日への新しい入力だけ」に絞ったところ、入力済みの日を直そうとして「保存できない」になった）。当日の分は本人と職長。
  職長・事務は、会社が入れた休み・有給・0.6補を出勤に変えることもできない（`canAdminEditEntry`。本人の入力か出勤の記録がある日だけ出勤にできる）
- 2026-10-01 時点で代行になる現場: 出光（倉本さん・とび）、川崎（梶原さん・とび）、葛西（靖仁さん・役員）
- 政仁さん・代表はマイページ（個人URL）からも最終承認・代行・却下ができる（`lib/foreman-todo.ts managerByToken`。
  ログインしたときと同じ役割判定 buildAuthUser + isManagerRole）

## 承認権限のロール制御（有給申請・帰国申請）

「現場レベルの作業は職長、最終承認は事業責任者」という原則をボタン表示レベルで実装。

### 承認ボタンの表示権限
| ボタン | admin | approver | foreman | 備考 |
|--------|-------|----------|---------|------|
| 職長承認 | ✓ | ✓ | ✓ | pending 状態の申請に対して表示 |
| 最終承認 | ✓ | ✓ | | foreman には「最終承認待ち」のラベルのみ表示 |
| 却下 | ✓ | ✓ | ✓ | 全員可能 |

- 適用画面: ダッシュボードの勤怠申請カード、および `/leave` の申請タブ
- foreman は foreman_approved 状態の申請に対して操作不可（読み取り専用で「最終承認待ち」と表示）
- 職長が直接「最終承認」する経路は UI レベルで遮断される

## 通知（/api/notifications）

`leaveRequests`（有給申請）と `homeLongLeave`（帰国申請）の両方を、`pending` + `foreman_approved` の合計件数でカウントする。

### 通知メッセージ書式
- `有給申請 X件 （職長待ちN / 最終承認待ちM）`
- `帰国申請 X件 （職長待ちN / 最終承認待ちM）`

### ロール別の意味づけ
- admin / approver: 職長待ち・最終承認待ちの両方が自分の対応対象（最終承認は admin / approver のみが押せるため）
- foreman: 自分の対応待ちは pending（職長待ち）分のみ。foreman_approved 分は参考表示
