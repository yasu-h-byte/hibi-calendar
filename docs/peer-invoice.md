# 応援の請求書

2026-09-25 社長指示。日比建設が「応援に行った」同業者（peer）へ送る請求書を、DEDURA＋ の中で
出面の実績から自動で組み立て、A4 で印刷（PDF化）できるようにしたもの。初回は 2026-09-25〜 の
梶原さん・川崎現場（応援 1名）から。

## これは何か

`/peer-statement`（同業者との請求・支払）は金額の**見込み**を一覧で見る画面。そこから実際に
相手へ送る**請求書そのもの**（A4・1ページ目が本体、2ページ目以降が出面明細）を作るのが
`/peer-invoice?company=<取引先id>&ym=YYYYMM`。

- 金額の計算は `/peer-statement` と完全に同じ数字（`lib/peer-statement.ts` の `buildPeerStatements`）を使う。
  鳶・土工の2行に割るときも合計が1円までズレないように調整している（`lib/peer-invoice.ts`）
- 出面明細（誰が・いつ・何人工働いたか）は、金額計算と同じ除外条件（有給・欠勤・現場休・帰国中・
  試験・出向者・休業補償(0.6)の除外、鳶/土工グループのみ集計）で作るので、明細の人工合計＋残業計の換算分
  （外国人 7h・日本人と外注 8h で1人工）が請求書本体の人工に一致する。印刷の注記も 2026-09-26 に
  「残業は換算して本体に含めている」に直した（それまで「人工には含んでいません」と実際と逆の注記だった）
- 印刷は **A4 縦のみ**で統一（請求書本体と出面明細を縦横混在させる案は Chrome の印刷崩れリスクが
  あるため見送り、代わりに出面明細は31日分を小さいフォントで縦向きに収めている）

## 発行・取り消し（凍結の仕組み）

**申請 → 承認（2026-09-26 代表指示「森田が発行→政仁が承認」）**: 事務（jimu・森田さん）は「発行を申請」まで。
申請した瞬間の内容を `pending`（番号なし）で凍結し、事業責任者・管理者が「承認して発行」すると番号が付いて
`issued` になる（承認時は再計算しない＝承認者が見た内容がそのまま発行される）。「差し戻し」（理由つき・`rejected`）
・「取り下げ」（申請者・`withdrawn`）は記録を残し、番号を消費しない。承認待ちは政仁さん・管理者の通知ベルに出る。
事業責任者・管理者は申請を経ずに直接発行もできる。経営コックピット（`/api/integration`）には発行済み・取り消し済みだけを渡す。

「下書き」の間は毎回その場で再計算した見込み。**「この内容で発行」を押すと、その瞬間の金額・
明細・宛先・自社情報をまるごと `peerInvoices` コレクションに凍結保存**し、以後この画面は
その凍結内容を描画するだけになる（あとで人員マスタや単価、取引先住所を変えても、発行済みの
請求書の内容は変わらない）。

- 番号は `${invoicePrefix}-${ym}-${NN}`（例: `HC-202609-01`）。**会社をまたいで月内で連番**
  （同じ月に別の会社へ発行しても番号は続く）
- 同じ会社・同じ月に発行済み（取り消されていない）ものがあれば、新規発行は拒否される。
  作り直す場合は先に「取り消し」を押してから、もう一度「発行」する
- 「取り消し」は状態を `void` にするだけで記録は残る（**取り消した番号は欠番のまま**。
  再利用しない）。取り消し理由は任意入力で履歴に残る
- 発行・取り消しは**事業責任者・管理者のみ**（`requireExecutiveAuth`。政仁さん個人パスワード
  または管理者パスワード）。閲覧・印刷は出面を触れる人なら誰でもできる

実装:
- 計算（純粋関数・Firestore アクセス無し）: `lib/peer-invoice.ts`
- Firestore 書き込み（発行・取り消し・採番）: `lib/peer-invoice-store.ts`
- API: `app/api/peer-invoice/route.ts`（`GET ?ym=&companyId=` で下書き/発行済み1件、
  `GET ?ym=` だけで月内の一覧、`POST { action: 'issue' | 'void' }`）
- 画面: `app/(app)/peer-invoice/page.tsx`
- テスト: `__tests__/peer-invoice.test.ts`（金額の整合性・支払期日・出面明細の合計）

## 社長が入力すること

### 1. 請求書の自社情報（設定 → 請求書の自社情報・管理者パスワード限定）

住所・登録番号・振込先は**わざと空欄のまま**にしてある。届いた請求書を見ながら、または
会社の登記情報・通帳を見ながらご自身で入力してください。

| 項目 | 説明 |
|---|---|
| 会社名・会社名（英字） | 既定 株式会社日比建設 / HIBI CONSTRUCTION |
| 郵便番号・住所・電話・FAX・メール | 発行者として印字される |
| 適格請求書発行事業者の登録番号 | `T` + 13桁。未入力だと発行できない |
| 振込先 | 銀行名・支店名・種別・口座番号・口座名義。未入力だと発行できない |
| 請求書番号の接頭辞 | 既定 `HC` |

未入力のまま「発行」を押すと、何が足りないかを画面にそのまま表示して止める
（`isCompanyProfileReadyForInvoice`）。

### 2. 相手会社（取引先マスタ → 元請・一次・同業の会社を編集）

取引先マスタの編集モーダルに、役割が「元請・一次・同業」のときだけ出る
「請求書の宛名（応援の請求書用・任意）」欄:

| 項目 | 説明 |
|---|---|
| 郵便番号・住所 | 宛名に印字。未入力なら空欄のまま印刷される（発行はブロックしない） |
| 敬称 | 既定「御中」 |
| 支払条件 | 月末締め固定。「翌月払い/翌々月払い」×「月末払い/5・10・15・20・25日払い」。支払日が土日祝なら前営業日に繰り上げて支払期日欄に印字する |

未設定の会社は既定で「翌月末払い」として計算される（`computeDueDate` のデフォルト）。

### 3. 工種ごとに単価が違う現場（鉄骨・仮設など・2026-09-25）

畠山組・川崎の応援のように、同じ現場でも担当する工事によって受取単価が違うことがある。
鉄骨工事は毎日あるとは限らず、何日か鉄骨をやったら仮設に戻り、また鉄骨が続く。
**決めごと（代表 2026-09-25）: 親現場そのものが仮設（普段の単価）、鉄骨工事だけ「工種」を作る。**

1. **現場マスタ**（`/sites`）で応援現場（親現場）の単価タブに、普段の単価（仮設）を入れる
2. 同じ現場の「＋ 工種を追加」で「鉄骨」を作り、その工種の単価タブに鉄骨の単価を入れる
3. **出面入力**（`/attendance`）で親現場を選ぶ。工種のある現場だけ、次が出る:
   - 日付の見出しに**その日の工種のチップ**（白＝親現場、色付き＝鉄骨など）。押して「鉄骨」を選ぶと、
     その日は全員が鉄骨として記録され、その日に入力済みの人の出面もまとめて鉄骨へ移る。列が色で塗られる
   - 上の**「期間で工種を切り替え」**で「26日〜30日は鉄骨」のように、まとめて決められる
   - 何もしていない日は親現場（仮設）のまま。普段どおり入力するだけでよい
4. その日だけ一人だけ違う工事をした、という**個別の例外**は、その人のマスの下のタグ（色付き）を押して選び直す
   （その人のその日だけ移る）。作業員ごとの「既定の工種」は名前の下にも残してあるが、
   普段は日付の見出しか期間指定だけで足りる
5. 請求書（`/peer-invoice`）は工種ごとに別の行・別の出面明細表になる（単価が違うため）。
   親現場（仮設）の分と鉄骨の分が、それぞれの単価で並ぶ

保存先の優先順位: 既に入っている現場 ＞ その日の工種 ＞ その人の既定 ＞ 親現場。
同じ人・同じ日が親現場と鉄骨の両方に入っている（入力ミス）場合は赤い警告が出る。
その人は「期間で切り替え」でも動かさずに名前を知らせるので、マスのタグでどちらかを選び直して解消する。

## HFU → 日比建設 の請求書（2026-09-26）

代表指示。HFU 所属の作業員が日比建設の仕事で働いた分を、HFU から日比建設へ請求する請求書。
応援の請求書と**同じ画面・同じ発行/取り消し/凍結の仕組み**で動き、違うのは次の点だけ。

| | 応援の請求書 | HFU → 日比建設 |
|---|---|---|
| 発行者 | 日比建設（`main.companyProfile`） | HFU（`main.hfuInvoice.profile`） |
| 宛先 | 同業者（取引先マスタ） | 日比建設（`main.companyProfile` の住所・御中） |
| 数える人 | 日比建設・HFU の作業員＋連れて行った外注 | **HFU 所属の作業員だけ**（外注・日比建設所属は入らない） |
| 対象の現場 | 応援現場だけ | **全現場**（自社現場・応援現場とも） |
| 単価 | 現場（工種）の受取単価 | 社内単価 鳶/土工の2つ（設定で入力） |
| 残業 | 人工に換算して含める | **「鳶 残業 ◯h × 残業単価」の別行**（残業単価 = 単価÷8×1.25・円未満四捨五入。30,000 → 4,688） |
| 発行日 | 発行ボタンを押した日 | **対象月の末日**（従来の手作り請求書どおり） |
| 番号 | `HC-202609-01` … | `HFU-202609-01` …（接頭辞ごとに別の連番。日比建設と同じ接頭辞は発行時に拒否） |
| 件名 | ◯月分 応援作業費 | ◯月分 作業費 |

- 開き方: `/peer-statement`（同業者との請求・支払）の上にある「HFU → 日比建設」→「請求書を作る」。
  URL は `/peer-invoice?company=__hfu_to_hibi__&ym=YYYYMM`
- 形は HFU がこれまで手作りしていた請求書（2025年12月分・笹塚駅南口東地区 鳶 94人工×30,000＋残業 4h×4,688
  ＝税込 3,122,627円。代表提供 2026-09-26）に合わせた。同じ数字になることをテストで確認している
- 人工の数え方は応援の請求書と同じ（有給・欠勤・現場休・帰国中・試験・出向者・休業補償(0.6)・鳶土工以外は除外、
  夜勤 1.5 人工）
- 請求額は出面明細の行から積み上げている（`lib/hfu-invoice.ts`）ので、明細と本体の人工は必ず一致する
- 発行に必要なもの: HFU の会社情報（会社名・住所・登録番号・振込先）、その月に使う単価（土工がいない月は土工の
  単価が空でもよい）。足りなければ何が足りないかを表示して止める。宛先（日比建設）の住所は「請求書の自社情報」から
  印字し、空なら空欄のまま（応援の請求書の宛先と同じ扱い）
- 経営コックピットへは `hfuInvoices[]` として `peerInvoices[]` とは分けて渡す（グループ内の請求を同業者からの
  入金と混ぜないため・`docs/integration.md`）
- 「自動」とは: 出面の実績から毎月の下書きが自動で組み上がること。発行ボタンは応援の請求書と同じく
  事業責任者・管理者が押す（承認フローの原則）

### 社長が入力すること（設定 → HFU → 日比建設 の請求書・管理者パスワード限定）

| 項目 | 説明 |
|---|---|
| 鳶 / 土工 1人工の単価 | 税抜。その月に使う単価が未入力（0）だと発行できない。残業単価はここから自動で出す |
| 支払月・支払日 | 月末締め。既定は翌月末払い（土日祝は前営業日） |
| HFU の会社情報 | 会社名・代表者・住所・電話・登録番号・振込先・請求書番号の接頭辞（既定 `HFU`） |

初めて開いたときは、従来の請求書に書いてある内容（会社名・代表者・住所・電話・登録番号・振込先・鳶 30,000円）が
入った状態で表示される。**「保存」を押すまでは保存されない**ので、内容を確かめてから保存する（FAX は読み取れなかったので空欄）。

実装: `lib/hfu-invoice.ts`（計算）・`lib/peer-invoice-store.ts` の `resolveInvoiceDraft`（下書きと発行の共通入口）・
テスト `__tests__/hfu-invoice.test.ts`

## データの置き場所

`main.companyProfile`（`demmen/main` 内・自社情報、`lib/compute.ts` の `CompanyProfile`）、
取引先マスタの `postal` / `address` / `honorific` / `paymentTerms`（同じく `main.subcons[]` の
各要素、`CompanyPaymentTerms`）、発行済み請求書は独立コレクション `peerInvoices`
（`demmen/main` には入れない。1件 = 1回の発行。`docs/firestore.md` 参照）。

## 経営コックピットとの連携

発行・取り消しした請求書は `GET /api/integration/monthly` の `peerInvoices[]` として
経営コックピットからも読める（`docs/integration.md`）。13週資金繰りの同業者からの入金予定は、
発行済みの `total`（税込）・`dueDate` をそのまま使える。
